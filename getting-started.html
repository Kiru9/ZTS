SNOWFLAKE QUICKSTART · 03 / 08

Snowflake 시작하기

한국어 번역본원문 기준 2026.09.21Tasty Bytes
교육 참석자용 · 외부 공유 및 재배포 금지

개요#

이 시나리오에서는 가상 웨어하우스를 살펴보고, 쿼리 결과 캐시를 사용하고, 기본적인 데이터 변환을 수행하고, Time Travel로 데이터를 복구하며, Resource Monitor와 Budget으로 계정을 모니터링하면서 Snowflake의 핵심 개념을 배웁니다.

학습할 내용#

  • 가상 웨어하우스를 생성하고 설정하며 크기를 조정하는 방법.
  • Query Result Cache를 활용하는 방법.
  • 개발에 Zero-Copy Cloning을 사용하는 방법.
  • 데이터를 변환하고 정제하는 방법.
  • UNDROP을 사용하여 삭제된 테이블을 즉시 복구하는 방법.
  • Resource Monitor를 생성하고 적용하는 방법.
  • 비용을 모니터링하는 Budget을 생성하는 방법.

구현할 내용#

  • Snowflake 가상 웨어하우스
  • Zero-Copy Cloning으로 생성한 테이블의 개발용 복제본
  • Resource Monitor
  • Budget

SQL 코드를 가져와 SQL 파일에 붙여 넣습니다.#

Snowflake에서 따라 하려면 이 파일의 SQL 코드를 복사하여 새 SQL 파일에 붙여넣으세요. 또는 아래 각 단계의 코드 블록을 차례로 복사해 실행하면서 진행해도 됩니다. 단, 실습 환경을 처음 상태로 되돌리는 초기화(reset) SQL은 파일 끝에만 있으므로, 실습을 반복하려면 파일의 마지막 부분을 실행하세요. SQL 파일의 끝까지 진행했다면 간단한 데이터 파이프라인 페이지로 건너뛸 수 있습니다.

가상 웨어하우스와 설정#

개요#

가상 웨어하우스는 Snowflake 데이터를 분석할 수 있도록 동적이고 확장 가능하며 비용 효율적인 컴퓨팅 성능을 제공합니다. 기본 기술의 세부 사항에 대해 걱정할 필요 없이 모든 데이터 처리 요구를 충족하는 것이 가상 웨어하우스의 목적입니다.

1단계 - 컨텍스트 설정하기#

먼저 세션 컨텍스트를 설정하겠습니다. 쿼리를 실행하려면 SQL 파일 상단의 쿼리 세 개를 선택한 다음 "► Run" 버튼을 클릭합니다.

SQL
ALTER SESSION SET query_tag = '{"origin":"sf_sit-is","name":"tb_zts,"version":{"major":1, "minor":1},"attributes":{"is_quickstart":1, "source":"tastybytes", "vignette": "getting_started_with_snowflake"}}';

USE DATABASE tb_101;
USE ROLE accountadmin;

2단계 - 웨어하우스 생성하기#

첫 번째 웨어하우스를 생성해 보겠습니다! 이 명령은 처음에는 일시 중단된 상태인 새 X-Small 웨어하우스를 생성합니다.

SQL
CREATE OR REPLACE WAREHOUSE my_wh
    COMMENT = 'My TastyBytes warehouse'
    WAREHOUSE_TYPE = 'standard'
    WAREHOUSE_SIZE = 'xsmall'
    MIN_CLUSTER_COUNT = 1
    MAX_CLUSTER_COUNT = 2
    SCALING_POLICY = 'standard'
    AUTO_SUSPEND = 60
    INITIALLY_SUSPENDED = true
    AUTO_RESUME = false;

가상 웨어하우스: 흔히 간단히 “웨어하우스”라고 부르는 가상 웨어하우스는 Snowflake의 컴퓨팅 리소스 클러스터입니다. 쿼리, DML 작업 및 데이터 로딩에는 웨어하우스가 필요합니다. 자세한 내용은 웨어하우스 개요를 참조하세요.

3단계 - 웨어하우스 사용 및 재개하기#

웨어하우스를 생성했으니 이제 세션의 활성 웨어하우스로 설정해야 합니다. 다음 구문을 실행합니다.

SQL
USE WAREHOUSE my_wh;

아래 쿼리를 실행하면 실패합니다. 웨어하우스가 일시 중단되어 있고 AUTO_RESUME이 활성화되어 있지 않기 때문입니다.

SQL
SELECT * FROM raw_pos.truck_details;

웨어하우스를 재개하고 이후에는 자동으로 재개되도록 설정하겠습니다.

SQL
ALTER WAREHOUSE my_wh RESUME;
ALTER WAREHOUSE my_wh SET AUTO_RESUME = TRUE;

이제 쿼리를 다시 실행해 보세요. 정상적으로 실행될 것입니다.

SQL
SELECT * FROM raw_pos.truck_details;

4단계 - 웨어하우스 확장하기#

Snowflake의 웨어하우스는 탄력적으로 확장되도록 설계되었습니다. 더 많은 리소스가 필요한 워크로드를 처리하도록 웨어하우스 크기를 즉시 늘릴 수 있습니다. 웨어하우스를 X-Large로 확장해 보겠습니다.

SQL
ALTER WAREHOUSE my_wh SET warehouse_size = 'XLarge';

더 커진 웨어하우스에서 트럭 브랜드별 총매출을 계산하는 쿼리를 실행해 보겠습니다.

SQL
SELECT
    o.truck_brand_name,
    COUNT(DISTINCT o.order_id) AS order_count,
    SUM(o.price) AS total_sales
FROM analytics.orders_v o
GROUP BY o.truck_brand_name
ORDER BY total_sales DESC;

Query Result Cache#

개요#

이제 Snowflake의 또 다른 강력한 기능인 Query Result Cache를 살펴보도록 하겠습니다. '트럭별 매출' 쿼리를 처음 실행했을 때는 몇 초 정도 걸렸을 것입니다. 완전히 동일한 쿼리를 다시 실행하면 거의 즉시 결과를 얻을 수 있습니다. 쿼리 결과가 Snowflake의 Query Result Cache에 캐시되었기 때문입니다.

1단계 - 쿼리 다시 실행하기#

이전 단계의 '트럭별 매출' 쿼리를 동일하게 실행합니다. 쿼리 세부 정보 창에서 실행 시간을 확인하세요. 훨씬 빨라졌을 것입니다.

SQL
SELECT
    o.truck_brand_name,
    COUNT(DISTINCT o.order_id) AS order_count,
    SUM(o.price) AS total_sales
FROM analytics.orders_v o
GROUP BY o.truck_brand_name
ORDER BY total_sales DESC;

Query Result Cache: 모든 쿼리의 결과는 24시간 동안 유지됩니다. 결과 캐시에 적중하면 컴퓨팅 리소스가 거의 필요하지 않으므로 자주 실행하는 보고서나 대시보드에 적합합니다. 캐시는 클라우드 서비스 계층에 있으므로 계정의 모든 사용자와 웨어하우스에서 공통으로 액세스할 수 있습니다. 자세한 내용은 지속형 쿼리 결과 사용에 관한 설명서를 참조하세요.

2단계 - 크기 축소하기#

이제 더 작은 데이터 세트를 다룰 예정이므로 크레딧을 절약하도록 웨어하우스 크기를 다시 X-Small로 줄이겠습니다.

SQL
ALTER WAREHOUSE my_wh SET warehouse_size = 'XSmall';

기본적인 변환 기법#

개요#

이 섹션에서는 데이터를 정제하는 기본적인 변환 기법을 살펴보고 Zero-Copy Cloning으로 개발 환경을 생성합니다. 목표는 푸드 트럭의 제조사를 분석하는 것이지만, 현재 이 데이터는 VARIANT 컬럼 안에 중첩되어 있습니다.

1단계 - Zero-Copy Cloning으로 개발용 테이블 생성하기#

먼저 truck_build 컬럼을 살펴보겠습니다.

SQL
SELECT truck_build FROM raw_pos.truck_details;

이 테이블에는 각 트럭의 제조사, 모델, 연식에 대한 데이터가 포함되어 있지만, VARIANT라는 특수 데이터 타입 안에 중첩되어 있거나 내장되어 있습니다. 이 컬럼에 연산을 수행하여 해당 값을 추출할 수 있지만, 먼저 테이블의 개발용 복제본을 생성하겠습니다.

truck_details 테이블의 개발용 복제본을 생성해 보겠습니다. Snowflake의 Zero-Copy Cloning을 사용하면 추가 스토리지 없이 원본과 동일하면서 완전히 독립적인 테이블 복제본을 즉시 생성할 수 있습니다.

SQL
CREATE OR REPLACE TABLE raw_pos.truck_dev CLONE raw_pos.truck_details;

Zero-Copy Cloning: 복제는 스토리지를 중복 사용하지 않고 데이터베이스 오브젝트의 복제본을 생성합니다. 원본이나 복제본에 적용한 변경 사항은 새로운 마이크로 파티션으로 저장되며, 다른 쪽 오브젝트에는 영향을 주지 않습니다.

2단계 - 새 컬럼 추가 및 데이터 변환하기#

안전한 개발용 테이블을 준비했으니 year, make, model 컬럼을 추가하겠습니다. 그런 다음 truck_build VARIANT 컬럼에서 데이터를 추출하여 새 컬럼에 채워 넣습니다.

SQL
-- 새 컬럼을 추가합니다
ALTER TABLE raw_pos.truck_dev ADD COLUMN IF NOT EXISTS year NUMBER;
ALTER TABLE raw_pos.truck_dev ADD COLUMN IF NOT EXISTS make VARCHAR(255);
ALTER TABLE raw_pos.truck_dev ADD COLUMN IF NOT EXISTS model VARCHAR(255);

-- 데이터를 추출하고 업데이트합니다
UPDATE raw_pos.truck_dev
SET 
    year = truck_build:year::NUMBER,
    make = truck_build:make::VARCHAR,
    model = truck_build:model::VARCHAR;

3단계 - 데이터 정제하기#

트럭 제조사별 분포를 확인하는 쿼리를 실행해 보겠습니다.

SQL
SELECT 
    make,
    COUNT(*) AS count
FROM raw_pos.truck_dev
GROUP BY make
ORDER BY make ASC;

마지막 쿼리의 결과에서 이상한 점을 발견했나요? 'Ford'와 'Ford_'가 서로 다른 제조사로 처리되는 데이터 품질 문제가 있습니다. 간단한 UPDATE 구문으로 쉽게 수정해 보겠습니다.

SQL
UPDATE raw_pos.truck_dev
    SET make = 'Ford'
    WHERE make = 'Ford_';

여기서는 로우의 make 값이 Ford가 되도록, 값이 Ford_인 모든 로우를 변경하도록 지정합니다. 이렇게 하면 Ford 제조사 값에 밑줄이 남지 않아 제조사별 개수를 일관되게 집계할 수 있습니다.

4단계 - SWAP으로 프로덕션에 반영하기#

이제 개발용 테이블의 데이터가 정제되고 올바른 형식으로 정리되었습니다. SWAP WITH 명령으로 이를 즉시 새 프로덕션 테이블로 전환할 수 있습니다. 이 명령은 두 테이블을 원자적으로 교환합니다.

SQL
ALTER TABLE raw_pos.truck_details SWAP WITH raw_pos.truck_dev;

5단계 - 정리하기#

교환이 완료되었으므로 새 프로덕션 테이블에서 불필요한 truck_build 컬럼을 삭제할 수 있습니다. 현재 이름이 truck_dev인 기존 프로덕션 테이블도 삭제해야 합니다. 하지만 다음 학습을 위해 기본 테이블을 "실수로" 삭제하겠습니다.

SQL
ALTER TABLE raw_pos.truck_details DROP COLUMN truck_build;

-- 프로덕션 테이블을 실수로 삭제합니다!
DROP TABLE raw_pos.truck_details;

6단계 - UNDROP으로 데이터 복구하기#

이런! 프로덕션 truck_details 테이블을 실수로 삭제했습니다. 다행히 Snowflake의 Time Travel 기능을 사용하면 즉시 복구할 수 있습니다. UNDROP 명령은 삭제된 오브젝트를 복원합니다.

7단계 - 삭제 확인하기#

테이블에 대해 DESCRIBE 명령을 실행하면 테이블이 존재하지 않는다는 오류가 발생합니다.

SQL
DESCRIBE TABLE raw_pos.truck_details;

8단계 - UNDROP으로 테이블 복원하기#

truck_details 테이블을 삭제 직전과 정확히 동일한 상태로 복원해 보겠습니다.

SQL
UNDROP TABLE raw_pos.truck_details;

Time Travel & UNDROP: Snowflake Time Travel을 사용하면 정해진 기간 내 어느 시점의 과거 데이터든 액세스할 수 있습니다. 이를 통해 수정되거나 삭제된 데이터를 복원할 수 있습니다. UNDROP은 실수로 삭제한 오브젝트를 매우 쉽게 복구할 수 있게 해 주는 Time Travel 기능입니다.

9단계 - 복원 확인 및 정리하기#

테이블을 조회하여 성공적으로 복원되었는지 확인합니다. 그런 다음 실제 개발용 테이블인 truck_dev를 안전하게 삭제할 수 있습니다.

SQL
-- 테이블이 복원되었는지 확인합니다
SELECT * from raw_pos.truck_details;

-- 이제 실제 truck_dev 테이블을 삭제합니다
DROP TABLE raw_pos.truck_dev;

Resource Monitor#

개요#

컴퓨팅 사용량을 모니터링하는 것은 매우 중요합니다. Snowflake는 웨어하우스의 크레딧 사용량을 추적하는 Resource Monitor를 제공합니다. 크레딧 할당량을 정의하고 임계값에 도달했을 때 알림이나 일시 중단 등의 작업을 트리거할 수 있습니다.

1단계 - Resource Monitor 생성하기#

my_wh에 사용할 Resource Monitor를 생성해 보겠습니다. 이 모니터의 월간 할당량은 100크레딧이며, 할당량의 75%에 도달하면 알림을 보내고 90%와 100%에 도달하면 웨어하우스를 일시 중단합니다. 먼저 역할이 accountadmin인지 확인하세요.

SQL
USE ROLE accountadmin;

CREATE OR REPLACE RESOURCE MONITOR my_resource_monitor
    WITH CREDIT_QUOTA = 100
    FREQUENCY = MONTHLY
    START_TIMESTAMP = IMMEDIATELY
    TRIGGERS ON 75 PERCENT DO NOTIFY
             ON 90 PERCENT DO SUSPEND
             ON 100 PERCENT DO SUSPEND_IMMEDIATE;

2단계 - Resource Monitor 적용하기#

모니터를 생성했으면 my_wh에 적용합니다.

SQL
ALTER WAREHOUSE my_wh 
    SET RESOURCE_MONITOR = my_resource_monitor;

각 설정이 제어하는 항목에 대한 자세한 내용은 Resource Monitor 사용 설명서를 참조하세요.

여기에서는 SQL로 Resource Monitor를 생성했지만 Admin » Cost Management » Resource Monitors 메뉴에서도 생성,관리가 가능합니다.

Budget 생성하기#

개요#

Resource Monitor가 웨어하우스 사용량을 추적하는 반면, Budget은 모든 Snowflake 비용을 더 유연하게 관리할 수 있는 방법을 제공합니다. Budget은 모든 Snowflake 오브젝트의 지출을 추적하고 달러 금액 임계값에 도달하면 사용자에게 알릴 수 있습니다.

1단계 - SQL로 Budget 생성하기#

먼저 SQL로 Budget 오브젝트를 생성하겠습니다.

SQL
CREATE OR REPLACE SNOWFLAKE.CORE.BUDGET my_budget()
    COMMENT = 'My Tasty Bytes Budget';

2단계 - Snowsight의 Budget 페이지#

Snowsight의 Budget 페이지를 살펴보겠습니다.

Admin » Cost Management » Budgets로 이동합니다.

  1. 웨어하우스 컨텍스트
  2. Cost Management 탐색 메뉴
  3. 기간 필터
  4. 주요 지표 요약
  5. 지출 및 예측 추세 차트
  6. Budget Details

3단계 - Snowsight에서 Budget 설정하기#

Budget은 Snowsight UI에서 설정합니다.

  1. 계정 역할이 ACCOUNTADMIN으로 설정되어 있는지 확인합니다. 왼쪽 하단 모서리에서 변경할 수 있습니다.
  2. 앞서 생성한 MY_BUDGET Budget을 클릭합니다.
  3. Budget Details를 클릭하여 Budget 세부 정보 패널을 연 다음 오른쪽 Budget Details 패널에서 Edit을 클릭합니다.
  4. Budget을 100으로 설정합니다.
  5. 알림을 받을 인증된 이메일 주소를 입력할 수도 있습니다. 사전에 사용자 프로필에 해당 이메일이 설정되어 있어야 합니다.
  6. Resources를 클릭하고 모니터링할 TB_101.ANALYTICS 스키마와 TB_DE_WH 웨어하우스를 추가합니다.
  7. Next 클릭 후 Save를 클릭합니다.

Budget에 대한 자세한 가이드는 Snowflake Budget 설명서를 참조하세요.
