Horizon을 활용한 거버넌스

한국어 번역본원문 기준 2026.09.21Tasty Bytes
교육 참석자용 · 외부 공유 및 재배포 금지

개요#

이 시나리오에서는 Snowflake Horizon의 강력한 거버넌스 기능 중 일부를 살펴봅니다. 먼저 역할 기반 액세스 제어(RBAC)를 살펴본 다음, 자동 데이터 분류, 컬럼 수준 보안을 위한 태그 기반 마스킹 정책, 로우 액세스 정책, 데이터 품질 모니터링, 마지막으로 Trust Center를 통한 계정 전체 보안 모니터링과 같은 기능을 자세히 알아봅니다.

학습할 내용#

  • Snowflake의 역할 기반 액세스 제어(RBAC) 기본 개념.
  • 민감한 데이터를 자동으로 분류하고 태그를 지정하는 방법.
  • Dynamic Data Masking으로 컬럼 수준 보안을 구현하는 방법.
  • Row Access Policy로 로우 수준 보안을 구현하는 방법.
  • Data Metric Function으로 데이터 품질을 모니터링하는 방법.
  • Trust Center로 계정 보안을 모니터링하는 방법.

구현할 내용#

  • 권한이 부여된 사용자 지정 역할.
  • PII에 자동으로 태그를 지정하는 데이터 분류 프로파일.
  • 문자열 및 날짜 컬럼을 위한 태그 기반 마스킹 정책.
  • 국가별로 데이터 가시성을 제한하는 로우 액세스 정책.
  • 데이터 무결성을 확인하는 사용자 지정 Data Metric Function.

역할 및 액세스 제어#

개요#

Snowflake의 보안 모델은 역할 기반 액세스 제어(RBAC)와 임의 액세스 제어(DAC) 프레임워크를 기반으로 구축되었습니다. 액세스 권한은 역할에 할당되고, 해당 역할은 다시 사용자에게 할당됩니다. 이를 통해 오브젝트를 보호하기 위한 강력하고 유연한 계층 구조가 만들어집니다.

액세스 제어 개요: 보안 설정이 가능한 오브젝트, 역할, 권한, 사용자를 비롯한 Snowflake 액세스 제어의 핵심 개념을 자세히 알아보세요.

1단계 - 컨텍스트 설정 및 기존 역할 확인#

먼저 이 실습의 컨텍스트를 설정하고 계정에 이미 존재하는 역할을 확인해 보겠습니다.

SQL
USE ROLE useradmin;
USE DATABASE tb_101;
USE WAREHOUSE tb_dev_wh;

SHOW ROLES;

2단계 - 사용자 지정 역할 생성#

이제 사용자 지정 tb_data_steward 역할을 생성합니다. 이 역할은 고객 데이터를 관리하고 보호하는 책임을 맡습니다.

SQL
CREATE OR REPLACE ROLE tb_data_steward
    COMMENT = 'Custom Role';

시스템 역할과 사용자 지정 역할의 일반적인 계층 구조는 다음과 같습니다.

원문 텍스트
                                +---------------+
                                | ACCOUNTADMIN  |
                                +---------------+
                                  ^    ^     ^
                                  |    |     |
                    +-------------+-+  |    ++-------------+
                    | SECURITYADMIN |  |    |   SYSADMIN   |<------------+
                    +---------------+  |    +--------------+             |
                            ^          |     ^        ^                  |
                            |          |     |        |                  |
                    +-------+-------+  |     |  +-----+-------+  +-------+-----+
                    |   USERADMIN   |  |     |  | CUSTOM ROLE |  | CUSTOM ROLE |
                    +---------------+  |     |  +-------------+  +-------------+
                            ^          |     |      ^              ^      ^
                            |          |     |      |              |      |
                            |          |     |      |              |    +-+-----------+
                            |          |     |      |              |    | CUSTOM ROLE |
                            |          |     |      |              |    +-------------+
                            |          |     |      |              |           ^
                            |          |     |      |              |           |
                            +----------+-----+---+--+--------------+-----------+
                                                 |
                                            +----+-----+
                                            |  PUBLIC  |
                                            +----------+

Snowflake 시스템 정의 역할의 정의:

  • ORGADMIN: 조직 수준의 작업을 관리하는 역할입니다.
  • ACCOUNTADMIN: 시스템의 최상위 역할이며, 계정 내에서 제한되고 통제된 소수의 사용자에게만 부여해야 합니다.
  • SECURITYADMIN: 모든 오브젝트에 대한 권한 부여를 전역적으로 관리할 수 있으며, 사용자와 역할을 생성, 모니터링 및 관리할 수 있는 역할입니다.
  • USERADMIN: 사용자 및 역할 관리만 전담하는 역할입니다.
  • SYSADMIN: 계정에서 웨어하우스와 데이터베이스를 생성할 권한을 가진 역할입니다.
  • PUBLIC: PUBLIC은 모든 사용자와 역할에 자동으로 부여되는 의사 역할입니다. 보안 설정이 가능한 오브젝트를 소유할 수 있으며, 이 역할이 소유한 모든 오브젝트는 계정의 다른 모든 사용자와 역할이 사용할 수 있게 됩니다.

3단계 - 사용자 지정 역할에 권한 부여#

역할에 권한을 부여하지 않으면 할 수 있는 일이 많지 않습니다. securityadmin 역할로 전환하여 새 tb_data_steward 역할에 웨어하우스를 사용하고 데이터베이스 스키마와 테이블에 액세스하는 데 필요한 권한을 부여해 보겠습니다.

SQL
USE ROLE securityadmin;

-- 웨어하우스 사용 권한을 부여합니다
GRANT OPERATE, USAGE ON WAREHOUSE tb_dev_wh TO ROLE tb_data_steward;

-- 데이터베이스와 스키마 사용 권한을 부여합니다
GRANT USAGE ON DATABASE tb_101 TO ROLE tb_data_steward;
GRANT USAGE ON ALL SCHEMAS IN DATABASE tb_101 TO ROLE tb_data_steward;

-- 테이블 수준 권한을 부여합니다
GRANT SELECT ON ALL TABLES IN SCHEMA raw_customer TO ROLE tb_data_steward;
GRANT ALL ON SCHEMA governance TO ROLE tb_data_steward;
GRANT ALL ON ALL TABLES IN SCHEMA governance TO ROLE tb_data_steward;

4단계 - 새 역할 부여 및 사용#

마지막으로 자신의 사용자에게 새 역할을 부여합니다. 그런 다음 tb_data_steward 역할로 전환하고 쿼리를 실행하여 어떤 데이터에 액세스할 수 있는지 확인할 수 있습니다.

SQL
-- 자신의 사용자에게 역할을 부여합니다
SET my_user = CURRENT_USER();
GRANT ROLE tb_data_steward TO USER IDENTIFIER($my_user);

-- 새 역할로 전환합니다
USE ROLE tb_data_steward;

-- 테스트 쿼리를 실행합니다
SELECT TOP 100 * FROM raw_customer.customer_loyalty;

쿼리 결과를 보면 이 테이블에 개인 식별 정보(PII)가 많이 포함되어 있음을 알 수 있습니다. 다음 섹션에서는 이 정보를 보호하는 방법을 알아봅니다.

분류 및 자동 태깅#

개요#

데이터 거버넌스의 중요한 첫 단계는 민감한 데이터를 식별하고 분류하는 것입니다. Snowflake Horizon의 자동 태깅 기능은 스키마의 컬럼을 모니터링하여 민감한 정보를 자동으로 검색할 수 있습니다. 그런 다음 이러한 태그를 사용하여 보안 정책을 적용할 수 있습니다.

자동 분류: Snowflake가 일정에 따라 민감한 데이터를 자동으로 분류하여 대규모 거버넌스를 간소화하는 방법을 알아봅니다.

1단계 - PII 태그 생성 및 권한 부여#

accountadmin 역할을 사용하여 pii 태그를 governance 스키마에 생성합니다. 또한 tb_data_steward 역할에 분류를 수행하는 데 필요한 권한을 부여합니다.

SQL
USE ROLE accountadmin;

CREATE OR REPLACE TAG governance.pii;
GRANT APPLY TAG ON ACCOUNT TO ROLE tb_data_steward;

GRANT EXECUTE AUTO CLASSIFICATION ON SCHEMA raw_customer TO ROLE tb_data_steward;
GRANT DATABASE ROLE SNOWFLAKE.CLASSIFICATION_ADMIN TO ROLE tb_data_steward;
GRANT CREATE SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE ON SCHEMA governance TO ROLE tb_data_steward;

2단계 - 분류 프로필 생성#

이제 tb_data_steward 역할로 분류 프로필을 생성합니다. 이 프로필은 자동 태깅의 동작 방식을 정의합니다.

SQL
USE ROLE tb_data_steward;

CREATE OR REPLACE SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE
  governance.tb_classification_profile(
    {
      'minimum_object_age_for_classification_days': 0,
      'maximum_classification_validity_days': 30,
      'auto_tag': true
    });

3단계 - 시맨틱 범주를 PII 태그에 매핑#

다음으로, 분류 프로필이 governance.pii 태그를 적용할 컬럼을 지정하는 매핑을 정의합니다. 이 매핑은 SEMANTIC_CATEGORY가 NAME, PHONE_NUMBER, EMAIL 등 일반적인 PII 유형과 일치하는 모든 컬럼에 태그를 적용하도록 합니다.

SQL
CALL governance.tb_classification_profile!SET_TAG_MAP(
  {'column_tag_map':[
    {
      'tag_name':'tb_101.governance.pii',
      'tag_value':'pii',
      'semantic_categories':['NAME', 'PHONE_NUMBER', 'POSTAL_CODE', 'DATE_OF_BIRTH', 'CITY', 'EMAIL']
    }]});

4단계 - 분류 실행 및 결과 확인#

customer_loyalty 테이블에서 분류 프로세스를 수동으로 시작해 보겠습니다. 그런 다음 INFORMATION_SCHEMA를 쿼리하여 자동으로 적용된 태그를 확인할 수 있습니다.

SQL
-- 분류를 실행합니다
CALL SYSTEM$CLASSIFY('tb_101.raw_customer.customer_loyalty', 'tb_101.governance.tb_classification_profile');

-- 적용된 태그를 확인합니다
SELECT 
    column_name,
    tag_database,
    tag_schema,
    tag_name,
    tag_value,
    apply_method
FROM TABLE(INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS('raw_customer.customer_loyalty', 'table'));

PII로 식별된 컬럼에 이제 사용자 정의 governance.pii 태그가 적용되어 있는 것을 확인합니다.

마스킹 정책#

개요#

민감한 컬럼에 태그를 지정했으므로 이제 Dynamic Data Masking을 사용하여 보호할 수 있습니다. 마스킹 정책은 쿼리 시점에 사용자에게 원본 데이터를 보여 줄지, 마스킹된 데이터를 보여 줄지 결정하는 스키마 수준 오브젝트입니다. 이러한 정책을 pii 태그에 직접 적용할 수 있습니다.

컬럼 수준 보안: 컬럼 수준 보안에는 민감한 데이터를 보호하기 위한 Dynamic Data Masking과 External Tokenization이 포함됩니다.

1단계 - 마스킹 정책 생성#

문자열 데이터를 마스킹하는 정책과 날짜 데이터를 마스킹하는 정책, 두 가지를 생성합니다. 로직은 간단합니다. 사용자의 역할에 권한이 없는 경우, 즉 ACCOUNTADMIN 또는 TB_ADMIN이 아닌 경우 마스킹된 값을 반환합니다. 그렇지 않으면 원래 값을 반환합니다.

SQL
-- 민감한 문자열 데이터에 대한 마스킹 정책을 생성합니다
CREATE OR REPLACE MASKING POLICY governance.mask_string_pii AS (original_value STRING)
RETURNS STRING ->
  CASE WHEN
    CURRENT_ROLE() NOT IN ('ACCOUNTADMIN', 'TB_ADMIN')
    THEN '****MASKED****'
    ELSE original_value
  END;

-- 이제 민감한 DATE 데이터에 대한 마스킹 정책을 생성합니다
CREATE OR REPLACE MASKING POLICY governance.mask_date_pii AS (original_value DATE)
RETURNS DATE ->
  CASE WHEN
    CURRENT_ROLE() NOT IN ('ACCOUNTADMIN', 'TB_ADMIN')
    THEN DATE_TRUNC('year', original_value)
    ELSE original_value
  END;

2단계 - 태그에 마스킹 정책 적용#

태그 기반 거버넌스의 강점은 태그에 정책을 한 번만 적용하면 된다는 점입니다. 이렇게 하면 현재 해당 태그가 지정된 모든 컬럼은 물론, 앞으로 해당 태그가 지정되는 컬럼도 자동으로 보호됩니다.

SQL
ALTER TAG governance.pii SET
    MASKING POLICY governance.mask_string_pii,
    MASKING POLICY governance.mask_date_pii;

3단계 - 정책 테스트#

지금까지의 작업을 테스트해 보겠습니다. 먼저 권한이 없는 public 역할로 전환하고 테이블을 쿼리합니다. PII 컬럼이 마스킹되어 있어야 합니다.

SQL
USE ROLE public;
SELECT TOP 100 * FROM raw_customer.customer_loyalty;

이제 권한이 있는 tb_admin 역할로 전환합니다. 이제 데이터가 모두 보여야 합니다.

SQL
USE ROLE tb_admin;
SELECT TOP 100 * FROM raw_customer.customer_loyalty;

로우 액세스 정책#

개요#

Snowflake에서는 컬럼을 마스킹하는 것 외에도 로우 액세스 정책을 사용하여 사용자에게 표시되는 로우를 필터링할 수 있습니다. 이 정책은 정의한 규칙에 따라 각 로우를 평가하며, 규칙은 일반적으로 사용자의 역할이나 기타 세션 속성을 기반으로 합니다.

로우 수준 보안: 로우 액세스 정책은 쿼리 결과에 표시되는 로우를 결정하여 세밀한 액세스 제어를 가능하게 합니다.

1단계 - 정책 매핑 테이블 생성#

로우 액세스 정책에서 일반적으로 사용하는 패턴은 어떤 역할이 어떤 데이터를 볼 수 있는지 정의하는 매핑 테이블을 사용하는 것입니다. 역할을 해당 역할이 볼 수 있도록 허용된 country 값에 매핑하는 테이블을 생성합니다.

SQL
USE ROLE tb_data_steward;

CREATE OR REPLACE TABLE governance.row_policy_map
    (role STRING, country_permission STRING);

-- tb_data_engineer 역할이 'United States' 데이터만 볼 수 있도록 매핑합니다
INSERT INTO governance.row_policy_map
    VALUES('tb_data_engineer', 'United States');

2단계 - 로우 액세스 정책 생성#

이제 정책 자체를 생성합니다. 이 정책이 TRUE를 반환하여 해당 로우를 볼 수 있도록 허용하는 조건은 사용자의 역할이 관리자 역할이거나, 사용자의 역할이 매핑 테이블에 존재하면서 현재 로우의 country 값과 일치하는 경우입니다.

SQL
CREATE OR REPLACE ROW ACCESS POLICY governance.customer_loyalty_policy
    AS (country STRING) RETURNS BOOLEAN ->
        CURRENT_ROLE() IN ('ACCOUNTADMIN', 'SYSADMIN') 
        OR EXISTS 
            (
            SELECT 1 FROM governance.row_policy_map rp
            WHERE
                UPPER(rp.role) = CURRENT_ROLE()
                AND rp.country_permission = country
            );

3단계 - 정책 적용 및 테스트#

country 컬럼에 정책을 적용합니다. 이 컬럼은 customer_loyalty 테이블에 있습니다. 그런 다음 tb_data_engineer 역할로 전환하고 테이블을 쿼리합니다.

SQL
-- 정책을 적용합니다
ALTER TABLE raw_customer.customer_loyalty
    ADD ROW ACCESS POLICY governance.customer_loyalty_policy ON (country);

-- 정책을 테스트하기 위해 역할을 전환합니다
USE ROLE tb_data_engineer;

-- 테이블을 쿼리합니다
SELECT TOP 100 * FROM raw_customer.customer_loyalty;

이제 결과 집합에는 country가 'United States'인 로우만 포함되어야 합니다.

Data Metric Function#

개요#

데이터 거버넌스는 보안뿐만 아니라 신뢰성과 안정성에 관한 것이기도 합니다. Snowflake는 Data Metric Function(DMF)을 통해 데이터 무결성을 유지하도록 지원합니다. 시스템에서 정의한 DMF를 사용하거나 직접 생성하여 테이블에 대한 자동 품질 검사를 실행할 수 있습니다.

데이터 품질 모니터링: 기본 제공 및 사용자 정의 Data Metric Function을 사용하여 데이터의 일관성과 신뢰성을 확보하는 방법을 알아봅니다.

1단계 - 시스템 DMF 사용#

Snowflake의 기본 제공 DMF 몇 가지를 사용하여 order_header 테이블의 품질을 확인해 보겠습니다.

SQL
USE ROLE tb_data_steward;

-- NULL인 고객 ID의 비율을 반환합니다.
SELECT SNOWFLAKE.CORE.NULL_PERCENT(SELECT customer_id FROM raw_pos.order_header);

-- DUPLICATE_COUNT를 사용하여 중복된 주문 ID가 있는지 확인할 수 있습니다.
SELECT SNOWFLAKE.CORE.DUPLICATE_COUNT(SELECT order_id FROM raw_pos.order_header); 

-- 전체 주문의 평균 총주문 금액입니다.
SELECT SNOWFLAKE.CORE.AVG(SELECT order_total FROM raw_pos.order_header);

2단계 - 사용자 정의 DMF 생성#

특정 비즈니스 로직에 맞는 사용자 정의 DMF를 생성할 수도 있습니다. order_total이 unit_price * quantity와 같지 않은 주문을 검사하는 DMF를 생성해 보겠습니다.

SQL
CREATE OR REPLACE DATA METRIC FUNCTION governance.invalid_order_total_count(
    order_prices_t table(
        order_total NUMBER,
        unit_price NUMBER,
        quantity INTEGER
    )
)
RETURNS NUMBER
AS
'SELECT COUNT(*)
 FROM order_prices_t
 WHERE order_total != unit_price * quantity';

3단계 - DMF 테스트 및 일정 설정#

DMF를 테스트하기 위해 잘못된 레코드를 삽입해 보겠습니다. 그런 다음 함수를 호출하여 오류를 감지하는지 확인합니다. 삽입할 레코드는 단가가 $5인 품목 2개를 주문하면서 총가격이 올바른 금액인 $10이 아니라 $5로 되어 있습니다.

SQL
-- 총가격이 잘못된 레코드를 삽입합니다
INSERT INTO raw_pos.order_detail
SELECT 904745311, 459520442, 52, null, 0, 2, 5.0, 5.0, null;

-- 주문 상세 테이블에 대해 사용자 정의 DMF를 호출합니다.
SELECT governance.invalid_order_total_count(
    SELECT price, unit_price, quantity FROM raw_pos.order_detail
) AS num_orders_with_incorrect_price;

이 검사를 자동화하려면 DMF를 테이블과 연결하고 데이터가 변경될 때마다 자동으로 실행되도록 일정을 설정한 다음, order_detail 테이블에 추가할 수 있습니다.

SQL
ALTER TABLE raw_pos.order_detail
    SET DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES';

ALTER TABLE raw_pos.order_detail
    ADD DATA METRIC FUNCTION governance.invalid_order_total_count
    ON (price, unit_price, quantity);

Trust Center#

개요#

Trust Center는 Snowflake 계정 전체의 보안 위험을 모니터링하는 중앙 대시보드를 제공합니다. 예약된 스캐너를 사용하여 다중 요소 인증(MFA) 미설정, 과도한 권한이 부여된 역할, 비활성 사용자 등의 문제를 확인하고 권장 조치를 제공합니다.

Trust Center 개요: Trust Center는 계정의 보안 위험을 평가하고 모니터링하는 자동 검사를 지원합니다.

1단계 - 권한 부여 및 Trust Center로 이동#

먼저 ACCOUNTADMIN이 사용자 또는 역할에 TRUST_CENTER_ADMIN 애플리케이션 역할을 부여해야 합니다. 여기서는 tb_admin 역할에 부여합니다.

SQL
USE ROLE accountadmin;
GRANT APPLICATION ROLE SNOWFLAKE.TRUST_CENTER_ADMIN TO ROLE tb_admin;
USE ROLE tb_admin;

이제 Snowsight UI에서 Trust Center로 이동합니다.

  1. 왼쪽 탐색 모음에서 Monitoring 탭을 클릭합니다.
  2. Trust Center를 클릭합니다.

2단계 - 스캐너 패키지 활성화#

기본적으로 대부분의 스캐너 패키지는 비활성화되어 있습니다. 계정의 보안 상태를 종합적으로 파악할 수 있도록 활성화해 보겠습니다.

  1. Trust Center에서 Scanner Packages 탭을 클릭합니다.
  2. CIS Benchmarks를 클릭합니다.
  1. Enable Package 버튼을 클릭합니다.
  1. 모달 창에서 Frequency를 Monthly로 설정하고 Continue를 클릭합니다.
  1. Threat Intelligence 스캐너 패키지에도 이 과정을 반복합니다.

3단계 - 탐지 결과 검토#

스캐너가 실행되도록 잠시 기다린 후 Findings 탭으로 돌아갑니다.

  • 심각도별로 위반 사항을 요약한 대시보드가 표시됩니다.
  • 아래 목록에는 각 위반 사항, 해당 심각도, 이를 발견한 스캐너가 자세히 표시됩니다.
  • 위반 사항을 클릭하면 요약과 권장 해결 단계가 포함된 세부 정보 창이 열립니다.
  • 심각도, 상태 또는 스캐너 패키지별로 목록을 필터링하여 가장 중요한 문제에 집중할 수 있습니다.

이 강력한 도구를 통해 Snowflake 계정의 보안 상태를 지속적으로 파악하고 필요한 조치를 취할 수 있습니다.
